📋 技术验证结论（klinecharts / ECharts / Lightweight Charts 三方案对比）

结论先行：三个方案都能做，没有"完全做不到、必须自己手撸引擎"的方案。 差异主要在开发工作量和细节风险上，不在"能不能实现"上。如果要选一个， 推荐 klinecharts：它是专门为"K线 + 成交量/MACD等副图 + 移动端"这个场景做的开源库， 逐根追加数据、多副图、暗黑模式都是内置能力，工作量最小。

能力点klinecharts v10ECharts v6Lightweight Charts v5

"下一根"的触发方式 按你的要求，本demo只支持用户手动点击"下一根/上一根"，没有自动播放/定时器逻辑。图表引擎本身只负责"画一根"，和是否自动播放无关——如果以后产品上要做"根据用户历史操作时长自动回放"，只需要在外层加一个 setInterval 调用 nextBar()，图表层完全不用改。

⚠️ 关于"图表加载不出来"的修复说明

上一版demo里三个图表库是用 <script src="https://cdn.jsdelivr.net/..."> 静态引入的——如果你所在网络访问不了 jsdelivr（国内很常见）、或者是在某个应用内嵌的预览面板里打开（面板可能有内容安全策略，只放行部分CDN域名），三个库就都加载不出来，整个图表区域是空白的，而且不容易第一时间看出原因。

这一版已经改成运行时动态加载 + 多镜像自动重试：每个库依次尝试 npmmirror（阿里云npm镜像，国内通常最稳）→ jsdelivr → unpkg 等多个源，加载中/加载失败都会直接显示在对应的图表区域里（不再是只有底部日志才能看到），失败时还会列出具体是哪个源、什么错误，并给一个"重试"按钮。

如果换了这版之后仍然看不到图表，把图表区域里显示出来的具体错误信息截图/文字发我——这比"都看不到"能帮我精确定位到底是网络问题、CSP拦截问题、还是某个库API签名对不上。有一个大概率的可能性要提前说明：如果你是在 Cowork 的预览/图库面板里直接看这个文件，该面板出于安全考虑，可能只允许加载 cdnjs.cloudflare.com 这一个域名的外部脚本，本demo用到的三个库不一定都能在cdnjs上找到匹配版本；这种情况下最可靠的验证方式是把文件下载到本地，用手机/电脑上正常的浏览器（Chrome/Edge/Safari）直接打开，而不是在应用内嵌面板里看。

关于K线数据

默认仍然是本地模拟生成（几百根可配置，公式是带随机游走的OHLCV+成交量，纯前端计算不依赖网络，最稳）。按你的要求也加了一个"🌐 尝试加载真实历史数据"按钮，点击后会尝试从 stooq.com 的公开CSV接口拉取真实历史日线（演示用固定拉AAPL），成功会自动替换当前数据源并在图表标题旁的"数据来源"标签里显示；如果拉取失败（网络/跨域限制等），会在诊断日志里报出原因并自动保留原来的模拟数据，不会导致demo中断。这个接口的可用性同样取决于你打开页面时所在的网络环境，我在这个沙箱里同样无法帮你实测。

本次验证的边界说明（请务必读一下）

当前这个技术沙箱环境的出网策略只放行了 Anthropic 自身域名和极少数几个包管理镜像， 访问 cdn.jsdelivr.net、unpkg.com、registry.npmmirror.com、registry.npmjs.org、cdnjs.cloudflare.com、 stooq.com 等全部被这个沙箱的网关拒绝，所以图表库加载、真实数据拉取，我这边都没法在本环境里跑起来做真机验证，只能做到：核对官方文档确认API签名、语法检查、以及用mock对象把外层交互逻辑（点击下一根/上一根、tab切换保状态、生成数据、明暗主题、手机/平板/桌面响应式布局）完整跑通。图表库真实加载效果和真实数据接口的连通性，需要你在自己能上网的设备上第一次打开时帮忙确认。

🐛 实测踩坑记录（持续更新，截至 2026-08-14）

这里统一汇总迄今为止真机/浏览器实测中真实复现的bug（不含"理论上可能有风险"这类猜测）， 方便后续对照复测；每条都标了当前状态。

#方案问题根因状态
1 klinecharts 图表区域完全空白，加载失败 CDN URL 路径写错：用的是 dist/klinecharts.min.js，v10 实际发布路径是 dist/umd/klinecharts.min.js 已修复
2 klinecharts 控制台报错 applyNewData is not a function v10 彻底移除了v9的 applyNewData()/updateData() 直接推数据的方式，改成 setDataLoader({getBars, subscribeBar, unsubscribeBar}) 拉取式模型，是版本升级带来的breaking change，不是笔误 已修复
3 ECharts 放大后点"下一根"，缩放比例被重置回默认 pushOne/popOne/setTheme 每次都用硬编码的默认 dataZoom 区间重新 buildOption()，把用户手动缩放状态覆盖掉了 已修复（新增 getCurrentZoom() 读取当前缩放并透传回 buildOption）
4 klinecharts 取消勾选任意一个副图指标（哪怕只是叠加在主图上的BOLL），VOL/MACD/KDJ/成交额等全部副图会一起消失，ECharts和Lightweight Charts同样操作都正常 v10 removeIndicator() 真实签名是单个filter对象 {id?, name?, paneId?}，旧代码按"猜测的常见风格"写成了 removeIndicator(paneId, name) 两个位置参数——第一个字符串参数被当成filter对象整体解构，三个字段全读出undefined，等价于"不加任何过滤条件"，触发库内部"清空全部指标"的行为 已修复（改用 removeIndicator({id: 创建时返回的indicator id}) 精确指定要删除的单个指标；同时把 createIndicator 的返回值保存下来作为id，overlay和独立pane两种指标都覆盖到）
5 klinecharts 成交量/成交额柱子整个消失，不再显示为柱状，ECharts/Lightweight Charts同样想做"红空心/绿实心"效果没有这个问题 为了做"涨（红）空心、跌（绿）实心"，把全局指标样式 indicator.bars[0].style 直接改成了 'stroke'，但没有同时设置 borderColor——klinecharts渲染柱状指标图形时，style==='stroke' 只会画 borderColor，不设的话默认是透明色，等价于"什么都不画"，柱子因此整根消失 已修复（改用 registerIndicator 覆盖内置VOL、并同步调整自定义AMOUNT，通过 figures[].styles 回调按每根数据的涨跌单独返回 {style, color, borderColor}：跌用 style:'fill' 实心，涨用 style:'stroke' 且显式给 borderColor，和主图K线的空心/实心规则保持一致）

诚实说明：之前给klinecharts"显示/隐藏切换"打4分时，已经在备注里写了"v10的id/paneId获取方式没有100%确认，实测前留有一点不确定性"——但这只是提示了不确定性，没有真正拦住这个bug上线，说明"看官方文档写代码"和"过一遍真实点击交互"之间必须要有实测这一步，光凭读文档打分是不够的。上面表格第4、5条都已经在评分表里体现为扣分，后续任何新发现的真实bug都会同样处理：先如实记录，再看是否需要调整对应维度的分数。

📊 新增：副图指标显示/隐藏——三方案难度评分

评分标准统一为1-5分（5分=最省事），四个维度：① 内置支持度——库本身有没有现成的KDJ/BOLL/MACD； ② 显示隐藏切换——做"点一下按钮显示或隐藏某个指标"这个交互，API是不是天生就支持； ③ 自定义指标难度——成交额这种库里没有的指标，扩展机制好不好用； ④ 布局自适应——副图数量变化时，图表高度/分区要不要自己手动重新计算。

维度klinechartsEChartsLightweight Charts
内置支持度 5分 MA/VOL/MACD/KDJ/BOLL全部内置，一行 createIndicator('KDJ') 就有 2分 都没有，KDJ/BOLL/MACD全部要自己写公式计算（本demo已经全部手算好了） 1分 零内置，连最基础的MA都要自己算，是三个里最"裸"的
显示/隐藏切换 3分（实测踩过真实bug，已修复） createIndicator/removeIndicator 本身能力是有的，但之前一版代码把v10的 removeIndicator 错误当成 removeIndicator(paneId, name) 两个位置参数调用——真实签名其实是单个filter对象 removeIndicator({id?, name?, paneId?})。传两个位置参数时，第一个字符串参数会被当成整个filter对象解构，id/name/paneId全部读出undefined，等价于"无过滤条件"，导致取消勾选任意一个指标（哪怕只是叠加在主图上的BOLL）都会把VOL/MACD/KDJ/成交额等已创建的副图全部清空——这是实测中真实复现、而不是猜测的bug，已改用 removeIndicator({id: 创建时返回的indicator id}) 精确删除单个指标修复。扣1分是因为这类"位置参数 vs 单filter对象"的签名差异，官方指南页面本身没有明确写全，容易在没有真机验证的情况下踩坑。 3分 没有开关API，靠整体重建option实现，逻辑不难但要小心别把用户缩放状态重置了（这次真踩过一次坑） 5分 每个指标就是独立的series对象，series.applyOptions({visible:false}) 一行搞定，三个里最简单
自定义指标（成交额） 4分 官方有专门的 registerIndicator() 扩展机制，但要学一套新的配置格式，有一定上手成本 4分 就是再加一个bar系列，用已有数据直接画，反而是三个里最直白的 4分 同样是再加一个Histogram系列，和ECharts难度相当
布局自适应 5分 副图开关会自动新增/移除pane，高度自己重新分布，完全不用管 2分 副图数量一变，grid行数、每个xAxis/yAxis绑定的gridIndex、dataZoom联动范围全部要重新算，本demo这块代码量最大 3分 pane高度要手动分配；本demo为了省事选了"关闭的副图收起成一条30px窄条"而不是真的移除pane，视觉上不如klinecharts干净，但实现简单很多（官方其实提供 removePane()，真要做到和klinecharts一样干净是可以做到的，只是要多写状态管理代码）
综合平均分 4.25（2026-08-14 因实测踩坑从4.5下调） 2.75 3.25

结论没变，但要澄清一点：klinecharts分数高不代表它没bug，恰恰相反——三个方案里真实踩到的、会导致功能整体损坏的bug目前全部出在klinecharts身上（CDN路径404、v9→v10的数据接入API整体替换、removeIndicator签名误用、以及这次的成交量柱style='stroke'不设borderColor导致柱子消失），而且都是那种"照着旧写法/字面理解写代码，实际跑起来才会暴露"的坑，说明klinecharts v10文档和实际API之间的匹配度还有改进空间，选它意味着要预留更多"实测验证+读源码"的时间成本，不能只看官方指南就下结论。ECharts和Lightweight Charts这次实测下来反而更"老实"——ECharts虽然工作量最大，但API都是文档写什么就是什么，目前只在zoom状态保留上踩过一次坑；Lightweight Charts至今没有出现过一次因为API签名理解错误导致的功能性bug（但受限于HistogramSeries没有border字段，成交量/成交额做不出真正的空心柱，这是引擎能力局限不是bug）。如果最终选型除了"长期加指标的工作量"外，还很看重"betting on一个API稳定、文档可信度高的库"，这一条要重新纳入权衡，不能只看综合平均分的数字高低。

⚖️ 性能与知识产权授权评估（面向本地化部署场景，2026-08-14新增）

前提说明：本节评估假设最终产品采用本地化部署（自建服务器/内网环境，非依赖外部CDN）：图表库以 npm install 依赖形式打包进自己的前端构建产物，不像本demo为了跨环境测试方便而运行时动态加载多镜像CDN。这意味着前面记录的"CDN镜像加载失败"这类风险在正式生产环境中基本不存在；本节评估的是库本身打包后的运行时性能，以及知识产权/授权合规风险。

结论：三者许可证都允许免费商用，不存在"用了就要交钱"的授权费问题，主要差异集中在 Lightweight Charts 的强制品牌展示条款上——这不是可选项，是开源许可证的一部分，不展示就等于违反许可证。如果金手指这类双盲测试训练平台不希望在训练界面上暴露"由TradingView提供"这类第三方工具来源（担心暴露测试工具技术栈、或与自身品牌调性冲突），需要产品/法务侧提前确认能否接受，或联系TradingView洽谈商业授权豁免该义务（会有额外成本和周期）。klinecharts和ECharts没有这个问题，可以完全"静默"集成。性能上，如果当前阶段只是"点击逐根回放"（非高频实时行情），三者性能都够用，不是当前选型的瓶颈；但如果未来产品要接入真实盘口的高频推送，Lightweight Charts的性能设计目标最贴合这个场景。
